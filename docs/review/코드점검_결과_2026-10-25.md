### 2회차 — 정확성·버그
- **[2회차] F3 🔴** `app/core/jwt/tokens.py:92` `timedelta(days=REFRESH_TOKEN_EXPIRE_MINUTES)` → refresh 수명 **20160일(약 55년)**. 값 이름은 '분'.
  - 코멘트 초안: "`REFRESH_TOKEN_EXPIRE_MINUTES`(20160 = 14일)를 `days=` 로 넣어 55년짜리 토큰이 나갑니다. `minutes=` 로 바꿔 주세요. (login/ 실습본 README 의 '템플릿 버그 1' 과 같은 종류)"
- **[2회차] F4 🔴** `app/apis/v1/auth_routers.py:40` refresh 쿠키 `expires=access_token.exp` — Starlette 는 숫자 `expires` 를 "지금부터 N초"로 읽어서, 유닉스 시각(약 17억 초)이 들어가 쿠키가 **2083년**까지 산다.
  - 코멘트 초안: "`expires=` 에 절대 시각을 넣으면 '지금부터 N초'로 해석돼 쿠키가 56년 갑니다. `max_age=14일(초)` + `samesite="lax"` + `path="/api/v1/auth"` 를 권장합니다."
- **[7회차에서 발견 → 2회차 항목으로 분류] F5 🔴** `tokens.py:73` `timegm(dt.timetuple())` — 한국 시간(+09:00) 벽시계 값을 UTC 로 읽어 **모든 토큰의 exp 가 9시간 늦다.** access 60분 → 실제 **600분**. 체크리스트의 "로그인 토큰은 60분"과 다르고, 챗봇도 같은 exp 를 믿는다.
  - 코멘트 초안: "`timegm(dt.timetuple())` 은 시간대를 버립니다. `int(dt.timestamp())` 로 바꾸면 access 60분 · refresh 14일이 정확히 맞습니다(테스트 `test_access_token_lives_60_minutes_not_10_hours`)."
